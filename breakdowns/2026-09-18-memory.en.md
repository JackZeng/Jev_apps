# Context and memory filtering: how they work and compare

[简体中文](2026-09-18-memory.md) | **English**

First compiled: 2026-09-18; see each case for its source-review date. Status: **not independently reproduced**.

## Choosing an approach

Tool-history compaction filters the current conversation; memory retrieval filtering selects from an external memory store. Both reduce input at different stages. Evaluate retained information and task quality before comparing token reductions. Compact Adviser decides when to compact; the existing compactor decides what to compact; memory filtering decides what to retrieve. They act at different stages and can be combined; downstream task quality matters. The adverse Hermes evaluation highlights post-compaction recall, retained length, retrieval recovery and repeated compaction, not just one API call. Results for its port do not automatically transfer to other hosts.

## Workflow and mechanism

History or memory candidates plus current task → Jev relevance scores → select records → construct downstream context.

Selecting original text and generating a new summary have different failure modes: selection can omit information needed later, while rewriting can distort it. The reported 94% reduction is one quick test, not a default compression target. Updated compaction-plugin sources show budget-fitted conversation context with tool-output bodies omitted; its recording animation makes no API calls. Evaluate size reduction, downstream task quality, cache rebuilding and total cost separately. The case includes the new usage report and reviewer critique.

Individual input and implementation differences are documented in the linked cases. This is an application-level synthesis, not a claim that every implementation is identical or an account of Jev’s internal training architecture.
